## D06 mapping.xlsx

1. **原件事实：静态／即时原语需要不同控制配置。** Sheet1!AA13:AD13 为“有静态原语的Group”，AG13:AJ13 为“无静态原语的Group”。在 (0,2) 示例（Z16），AA16 为 `Send_PI_en = 1`，AA17 为 `Send_PI_num = 0`，AB17 明示“0表示1”；AA20／AA21 启用应答并用同类计数编码。无静态原语示例 (0,0)（AF16）的 AG23 为 `Back_sign_en = 1`，AG24 为 `Q = 1`。下面“其他”部分 AA32、AA36、AA39 又分别显示发送关闭、接收应答开启、返回应答关闭。**建议／模块：控制依赖 IR、配置校验**保留角色与编码语义，在采用同一协议版本时检查请求与应答配对。不能将计数寄存器 0 当作零请求，也不能由参数名猜出未填写的默认值。

## D12 ResNet50_5chip.xlsx

## D02 Detection 动态接收需求

7. **原件事实／推算：高度切分有重叠。** 第2页将 [0,256) 划成 [0,33)、[32,65)、[64,97)、[96,129)、[128,161)、[160,193)、[192,225)、[224,256)，前7块33行、末块32行。总计263行，比256多7行。按原式三通道、宽256计，发送元素总量为 `263×256×3 = 201984`，原输入为196608，重复5376元素，增加约2.734%。**推断／模块：算子分块与 halo 分析**这是相邻块共享边界行的证据；具体由哪个 kernel／stride 导致，材料未说明。只有确认数据类型每元素1B后才能将这些元素数称为字节数。

8. **原件事实／推算：每块分两个 phase，末 core 的量不同。** 第2页给出前7个 core 每 phase 为 `33×256×3/2 = 12672`，第8个为 `32×256×3/2 = 12288`，目的绝对 core 坐标依次 (8,4) 到 (15,4)。每 phase 合计100992元素，两次共201984。**建议／模块：phase 调度与发送清单**以每个目的 core 的实际分块量建表，避免平均分配；适用于这组固定输入需求，不能推广为任意模型均为两 phase。

9. **原件事实：布局契约依赖 0x81，轴说明有歧义。** 第2页写“256*256*3（通道*高度*宽度）”，但后续公式按33行、宽256、3通道使用；“数据高度拆8份，宽度拆分”也没有完整给出宽度区间。数据采用“0x81原语的数据存放方式”。**建议／模块：前端轴规范化、布局降级与主机输入协议**先确认真实 CHW／HWC、每 phase 的轴切分及 0x81 存储顺序，再形成发送计划。此页不足以验证 ONNX Conv 属性、端序、量化格式或接收内存地址。

## D14 Sound Tracking 动态接收需求

10. **原件事实／推算：补通道影响物理通信量。** 第2页把8×257×41补成16×257×41，前8通道真实、后8通道全零；宽度按1-based闭区间 1–10、11–20、21–30、31–41 切成10／10／10／11列，高度不拆。目的为 (0,0)–(3,0)。块量41120B／41120B／41120B／45232B，共168592B。原逻辑元素数84296，补后168592，原文给出的B值与每元素1B相符，但未说明有符号性。**建议／模块：通道对齐与通信成本**区分逻辑输入、补零后的物理输入，保留真实通道掩码；只有遵循同一主机传输契约时采用该补零方案，不能假定零通道会自动免传。

11. **原件事实／推算：四 phase 不等长，并有末包控制位。** 第2页前3个目的各为10240B、10240B、10240B、10400B；第4个为11264B、11264B、11264B、11440B。各块总和与上条一致，前三 phase 各41984B，末 phase 42640B。页内要求每个 phase 最后一个包的 P=1。全部数值可被16整除；10240=16×64×10、10400=16×65×10，仅提示64／64／64／65行的候选解释，不证明实际打包轴顺序。**建议／模块：packetizer 与控制校验**分别验证分块求和、phase求和及末包标志。需确认“最后一个包”是每目的流还是全局流，不能自行扩展成所有目的各置P的既定协议。

12. **原件事实：Trigger 后存在独立的跨片发送事件。** 第3页说 Trigger 上升沿后第一个 phase，紫色 core 向 FPGA 发送16B、2个路由包；红色 core 是代表 FPGA 的假想 core，不能计入物理 placement。图 image2 显示紫色标注“7，3”，image1（第2页）显示底行4个蓝色目的块，与页内坐标说明相符，但图的编号空间仍需确认。第3页 image3 的跨片包字段为 M=11（2b）、CoreID（4b）、Rsv（10b）、Payload（96b）、CRC（16b），合计128b；image4 的32bit包头 R[63:32] 为 S/T/P/Q 各1b、X/Y各8b、A为12b。正文指定 CoreID=4'd0、Payload[91:76]=16'd0，即该示例 X/Y为0。**建议／模块：外部事件调度与包编码**把 Trigger 后事件独立于张量数据边保存，按字段宽度核验地址打包。16B/2包支持该示例平均8B数据/路由包的推算，不足以证明所有包都装满。若输入也使用同一128b外包且每包携带8B有效数据，168592B对应21074包、337184B链路帧字节；这是条件估算，不含链路编码、间隙、重发或 Trigger 事件，未实测吞吐。

固定 core 坐标、Group 层号、phase 数、0x81布局和请求参数值均为实例约束，不是跨模型最优策略。没有性能对照、链路速率、容量规范、拥塞记录或运行正确性结果；98k、196K、11225、9331、30000 不可当作已知容量／字节量。颜色语义需图例或代码佐证，不能以彩色区域面积直接统计有效 core。D14 图像已查看，但整页的裁剪、连线、形状和母版没有完整视觉核验；D06／D12 网格只完成结构检查，placement 未被完整解读或验证。文档相关并不意味着协议版本一致。此专题也未验证 NIR 的 MaxPool、checkpoint 保存内容或 ONNX Loop 后端能力。

## 待验证问题与实验建议

- **分块语义**：确认 Detection 输入轴顺序、0x81存储布局和产生1行重叠的算子参数。建议用带唯一坐标编号的输入，人工对照8块与原图覆盖，检查共享行及输出裁剪；先做数据重排检查，不要求芯片仿真。
- **phase协议**：确认 Sound Tracking 末包P的作用域、四 phase 的分割轴及地址递增方式。建议核对每目的累计字节数、末phase余量、P位置，并对少包／重复包定义检测条件。
- **控制闭环**：核实即时请求计数的0编码、直接／间接目的、应答数量和 start_instant_PI_num 阈值语义。建议列出请求—接收—执行—应答的事件表，查找未配对依赖和等待环；PI_loop_en 的语义另查协议规范。
- **多片布局**：核实 D12 六个 chip 标签中的启用五片集合、Group1/18复用关系、Lxe和IB／OB定义。建议随后仅静态核对对应 resnet50top 的 group/core/phase配置及跨片端点，保存“表格证据／代码证据／仍未知”三列，本次没有执行这项核对。
- **成本模型**：将有效元素、halo重复、补零字节、包头／CRC与控制包分别计数；确认每元素字节数和满包策略后再算线上量。比较等宽与10/10/10/11切分时，必须同时检查资源约束与phase最大负载，不能从本材料声称延迟降低。
