# 行为仿真：怎么跑 + 每个输出文件是什么

> **这份文件是什么**：它是 [工具包学习指引.md](工具包学习指引.md) 里"建议的动手顺序"**第 1 步**的展开。第 1 步原文只有一句话——"先跑一遍 LeNet 的行为仿真，把 `TestEngine` 和 `ResultCompareWithClockSpecificSimulator` 用熟，目标是能看懂 `simulator/Out_files/LeNet_*/` 下的每一个输出文件"。这份文件就是那句话的操作手册。
>
> **读法**：第 0～2 步是"跑起来"，第 3～4 步是"看懂产物"，第 5 步是"拿它做调试"。不跑也能读，但建议边读边对着文件看。
>
> **本文所有数字都是我在这台机器上实测出来的**（一次独立复跑，`temp/out_files/LeNet_smoke1/` 与参考 run `temp/out_files/LeNet_002/` 逐字节一致，跑完已清理）。少数推断内容集中放在最后的"不确定项"里。

## 导语：跑一次行为仿真，实际发生了什么

这个项目里有**两套仿真器**，`TestEngine.run_test()` 一次调用会把它们串起来：

```
        map_config（嵌套字典）
                │
                ├─────────────────────────────┐
                ▼                             ▼
   ① behavior_simulator/  (纯 Python)   ② TianjicX1_SIM.exe (Verilog)
      把 map_config 解释成"每个 core      读 temp/config/{tb}Config.json，
      每个 phase 每个原语干什么"，        真跑硬件时序
      逐 phase 算出内存结果
                │                             │
                ▼                             ▼
      temp/out_files/{tb}/**         simulator/Out_files/{tb}/**
      （Python 侧产物）              （硬件侧产物）
                │                             │
                └────────► cmp_out/ ◄─────────┘
                     逐文件逐字节 diff，这才是"裁判"
```

三个要点，先记住：

1. **Python 侧产物全部落在 `temp/` 下**，硬件侧产物全部落在 `simulator/Out_files/` 下。**唯一的例外**是 `{tb}_description.txt`——它物理上在硬件目录里，但其实是 Python 写的（[behavior_simulator/chip.py:107-109](behavior_simulator/chip.py#L107-L109)）。
2. **判分点只有一处**：`cmp_out/` 目录。其余文件（`output/`、`Rcmd/`、`hwconfig`…）都是给人看的现场证据，`run_test()` 不看它们。
3. **在非 Windows 平台上 `run_test()` 不跑 `.exe`，直接 `return True`**（[test_engine/test_engine.py:39-43](test_engine/test_engine.py#L39-L43)）。所以你可以只跑 Python 侧来迭代 codegen——**这是你以后调 `onnx2prim` 最快的反馈环**。

## 第 1 步：两种跑法

### 1.1 现成入口：`generator/LeNet/g1_1core.py`

它自带 `__main__`，从数据准备到 `run_test()` 全包：

```bash

```

它做的事（[LeNet/g1_1core.py:153-229](LeNet/g1_1core.py#L153-L229)）：

| 步骤 | 代码 | 说明 |
|---|---|---|
| 1 | `LeNetDataHandler()` | 加载 `lenet_mnist_final_99.3.pth`，跑一遍 PyTorch 前向，抓每层输入/输出并量化 |
| 2 | `generate_data(handler)` | 用 `tensor_split` 把每层张量切成芯片可用的内存块 |
| 3 | `QuantizationConfig()` | 每个 `Cut` 的移位量（`fc_cut3` 是特例） |
| 4 | `gen_0/1/2_map_config(...)` + 三次 `add_config` | 造 G0/G1/G2 三组，偏移后落成 phase_group 0/1/2 |
| 5 | `add_router_info` → `add_prim_at_the_beginning` | 解析路由表头；给每组开头插一个 p06 soma2 |
| 6 | `TestEngine(map_config, test_config)` → `assert tester.run_test()` | 跑 |

**输入数据是固定的**：`LeNetDataHandler(seed=7)` 里输入是 `torch.randn((1,1,28,28))`（[LeNet/lenet_model/lenet_data_handler.py:19-21](LeNet/lenet_model/lenet_data_handler.py#L19-L21)），不是真实 MNIST 图片。好处是**结果完全可复现**（我复跑一次，产物与参考 run 逐字节一致）；代价是它测的是"链路通不通"，不是"识别准不准"。想喂真图片只有扁平的 `generator/lenet.py` 那条路（而且 `batch_test_lenet.py` 是**用正则改写源码文件**再跑的，动它之前先备份）。

### 1.2 最小自造驱动（这段是我实测跑通的）

想看清单条链路的每一环、又不想碰 `.exe`，就用这段。它会产出**和 `run_test()` 完全一样的 Python 侧产物**，但不跑 exe、不删任何已有目录：

```python
import numpy as np, sys, os, json
sys.path.append(os.getcwd())                       # cwd 必须是项目根

from generator.mapping_utils.map_config_gen import MapConfigGen
from generator.mapping_utils.prims import p06
from generator.LeNet.g0 import gen_0_map_config
from generator.LeNet.g2 import gen_2_map_config
from generator.LeNet.g1_1core import gen_1_map_config
from generator.LeNet.lenet_data import generate_data
from generator.LeNet.lenet_model.lenet_data_handler import LeNetDataHandler
from generator.LeNet.lenet_cut_config import QuantizationConfig
from generator.behavior_simulator import Simulator
from generator.code_generator import MapConfig
from generator.util import Path

tb = 'LeNet_smoke1'          # ← 换个名字，别覆盖参考输出
chip = (0, 0)

handler = LeNetDataHandler()
data = generate_data(handler)
cuts = QuantizationConfig()
config = MapConfigGen()

phase = np.ones(50).astype(int)                    # 与 g1_1core.__main__ 最终状态等价
config.add_config(gen_0_map_config(phase, 20_0000, size_x=1, size_y=1, data=data,
                                   out_data_en=True, chip=chip, in_data_en=False), core_offset=(1, 0))
config.add_config(gen_1_map_config(phase, 20_0000, size_x=1, size_y=1, in_cut_start_dict=cuts,
                                   in_data_en=True, out_data_en=True, chip=chip, data=data,
                                   init_data=True), core_offset=(0, 0))
config.add_config(gen_2_map_config(phase, 20_0000, size_x=8, size_y=1, data=data, in_data_en=True,
                                   out_data_en=True, chip=chip, init_data=True, send_to_fpga=True),
                  core_offset=(0, 1))
MapConfigGen.add_router_info(map_config=config.map_config)
MapConfigGen.add_prim_at_the_beginning(config.map_config, prim={
    'axon': None, 'soma1': None, 'router': None,
    'soma2': p06(addr_in=0x0000 >> 2, addr_out=0x8400, addr_ciso=0x10000 >> 2, length_in=1024,
                 num_in=12, length_ciso=1, num_ciso=12, length_out=1024, num_out=12,
                 type_in=1, type_out=1, data_in=None)})
config.map_config['sim_clock'] = 10_0000
config.map_config['step_clock'] = {((0, 0), 0): (10_0000 - 1, 10_0000)}

sim = Simulator(MapConfig(config.map_config), [(0, 1)])    # ← 注意要包一层 MapConfig
sim.map()
json.dump(sim.simulate(tb), open(Path.json_config_path(tb), 'w'), ensure_ascii=False, indent=4)
```

**实测结果**（`tianjic` 环境，整机 8 秒左右）：

```

...
core ((0, 0), (0, 0)) execution phase 6 static
OK LeNet_smoke1
```

产出了 `temp/out_files/LeNet_smoke1/`（10 个 `*_input/` + `output/` + `cmp_out/`，共 696 KB）+ `simulator/Out_files/LeNet_smoke1/LeNet_smoke1_description.txt`（33 KB）+ `temp/config/LeNet_smoke1Config.json`（4.4 MB）。这三个东西全部**逐字节等于**参考 run `LeNet_002` 的对应物。

**两个实测踩到的坑（都写在这里，省得你自己撞）**：

- `Simulator` 的第一个参数必须是 `MapConfig` 对象，**不能直接传字典**。传字典会在 `Simulator.__init__` 里炸：
  `AttributeError: 'dict' object has no attribute 'sim_clock'`（[behavior_simulator/simulator.py:19](behavior_simulator/simulator.py#L19)）。`TestEngine` 内部就是替你做了这件事（[test_engine.py:20](test_engine/test_engine.py#L20)：`MapConfig(map_config)`）。
- 运行时会打印一条 warning：
  `UserWarning: phase 0, src core: ((0, 0), (7, 1)), dst core: ((0, -13), (7, 3)) dst chip not exist!`
  **这是预期的，别当成自己的 bug**。`send_to_fpga=True` 时 G2 的第 7 号 core 用的是一个"走到 FPGA 口"的哨兵路由头（`addRHead(X=0, Y=-128, ...)`），`_get_real_core_idx` 按坐标环绕算出一个不存在的芯片，于是告警。**参考 run `LeNet_002` 也打了同一条。**

### 1.3 `test_config` 四个字段，一个都不能少

```python
from generator.test_engine import TestMode, TestEngine
from generator.test_engine.test_config import HardwareDebugFileSwitch

test_config = {
    'tb_name': 'LeNet_dbg1',                                    # 决定所有输出文件的名字前缀
    'test_mode': TestMode.MEMORY_STATE,                          # 两个分支返回同一对象，目前是死开关
    'debug_file_switch': HardwareDebugFileSwitch().close_all.dict,
    'test_group_phase': [(0, 1)],                                # 只有 cmp_out 的比对用它（见 5.3）

assert TestEngine(config.map_config, test_config).run_test()
```

- `debug_file_switch`：`HardwareDebugFileSwitch` 有 30 个字段（`DUMP_A_AD_INA`、`DUMP_STEP_NUM`、`DUMP_PHASE_NUM`…）。`.close_all` 关掉全部硬件调试转储，`.open_debug_message` / `.singla_chip` / `.multi_chip` / `.open_burst` 是几个预设。它只影响硬件侧多写哪些文件。
- `test_mode`：`MEMORY_STATE` 和 `PRIM_OUTPUT` 在 `construct_simulator()` 里返回的是**同一个** `Simulator`（[test_engine.py:47-51](test_engine/test_engine.py#L47-L51)），所以现在换它没有可观察差异。
- `test_group_phase` 的真实效果**和字面意思不一样**，见 5.3。

## 第 2 步：`run_test()` 内部调用链

```
TestEngine(map_config, test_config).run_test()                       test_engine/test_engine.py:24
  ├─ construct_simulator()                → Simulator(MapConfig(...), test_group_phase)      :25, 47-51
  ├─ simulator.map()                                                                            :27
  │    ├─ 遍历 (step_id, group_id, config)：建 Core、_add_PI_groups（按 PI_loop_num 铺开原语）  simulator.py:24-46
  │    ├─ 把每个原语的 memory_blocks 灌进 core 内存（_init_memory）                              simulator.py:118+
  │    ├─ chip.set_phase_clock(...)（每个 phase 多少 clock）                                     simulator.py:43
  │    └─ 解路由头（addRHead 的相对目标 → 真实 core）                                            simulator.py:68
  ├─ Path.delete_all × 3                → 删 temp/out_files/{tb}、simulator/Out_files/{tb}、simulator/Debug_files
  ├─ simulator.simulate(tb_name)                                                                :31
  │    └─ chip_array.simulate(tb)                                                               chip_array.py:14
  │         ├─ chip.print_case_spec(tb)   → simulator/Out_files/{tb}/{tb}_description.txt
  │         │                            → temp/out_files/{tb}/{core_x}_{core_y}_input/*.txt
  │         └─ chip.simulate(tb)  逐 core 逐 phase：
  │              ├─ core.simulate(...)   真正算内存结果
  │              ├─ print_core_phase_output → temp/out_files/{tb}/output/output_((cx,cy),(x,y))@{phase+1}.txt
  │              │                          → temp/out_files/{tb}/cmp_out/cmp_out_...@{step}_{phase}.txt
  │              └─ OutputFileGenerator.output → temp/out_files/{tb}/output/output_{group}@{phase+1}.txt
  ├─ json.dump(json_config, temp/config/{tb}Config.json)   ← 加 debug_file_switch                   :32-35
  └─ if platform.system() == 'Windows':                                                          :39
       ├─ HardwareProxy.execute(tb)  → cd simulator; TianjicX1_SIM.exe <json绝对路径> <tb>
       │                               → 写满 simulator/Out_files/{tb}/**
       └─ compare_cmp_out_dir_result() → diff temp/out_files/{tb}/cmp_out/ 与 simulator/Out_files/{tb}/cmp_out/
     else:
       └─ return True                 ← 完全不碰 exe
```

三个细节值得单独记：

- **exe 的调用形式**是 `TianjicX1_SIM.exe <temp/config/{tb}Config.json 的绝对路径> <tb_name>`（[util/command.py:10-12](util/command.py#L10-L12)）。也就是说 **JSON 是 Python 交给硬件仿真的唯一输入**——`simulator/LeNet_002Config.json` 那份 4.3 MB 的副本是历史的，每次跑真正用的是 `temp/config/` 下的。
- **`simulate()` 里对 chip 的遍历是硬编码单芯片的**：`for y in range(4): for x in range(4)` 且带注释 `# FIXME 只支持3*3阵列`，`if (0, 0) not in self._chip_array`（[simulator.py:29, 45](behavior_simulator/simulator.py#L29)）。多芯片支持是不完整的，你的 `onnx2prim` 在早期不必碰多芯片。
- `phase_num` 在这条链路上有**两套编号**（0 起 / 1 起），是这份文档里最容易搞错的地方，见 4.3 与 4.4。

## 第 4 步：每一个输出文件的解说

### 4.0 先看哪几个（阅读优先级）

| 想知道什么 | 看哪个 |
|---|---|
| 我生成的映射，到底把每个原语配成了什么参数？ | **`{x}_{y}_input/*.txt`**（这是 codegen 调试的第一现场） |
| 这个用例的规模对不对（几个 phase group、每个 phase 多少 clock）？ | `{tb}_description.txt` |
| 数据流经每个 phase 后，内存里到底变成了什么？地址对不对？ | `output/output_*.txt` |
| 我的映射和手写映射/硬件，结果一致吗？ | `cmp_out/*.txt` |
| 这个 phase 花了多少时钟？ | `cmp_out/phase_cnt.txt` |
| 硬件到底往哪个地址写了什么配置？ | `cRcmd/`、`chwconfig_0_0.txt` |

### 4.1 `temp/out_files/{tb}/{x}_{y}_input/{phase}_{PrimName}_{PIChex}.txt`

**这是最有用的一个目录，也是最少人提到的。** 它是"Python 认为每个 core、每个 phase、每个原语该被配成什么样"的**人读视图**，直接对应硬件寄存器。

- 目录名 `{x}_{y}` 是 **core 坐标**（不是 chip 坐标）。LeNet_002 有 10 个：`0_0`(G1)、`1_0`(G0)、`0_1`～`7_1`(G2 的 8 个核)。
- 文件名 = `{phase}_{原语槽位}_{PIC 十六进制}`，`phase` **从 0 起**。槽位名就是 `Axon`/`Soma1`/`Router`/`Soma2`。
- 内容：`key = value` 一行一项；Router 文件的末尾还有一段用 `****` 隔开的**地址尾注**（字节地址）。

举个真实的例子，`0_0_input/1_Router_0x9.txt`（core (0,0) 的 phase 1，PIC=9 路由器）：

```
PIC = 9
Rhead_mode = 1
CXY = 0
Send_en = 1
Receive_en = 1
Dout_Mem_sel = 1
Addr_Dout_base = 1024
Addr_Dout_length = 0
Addr_Rhead_base = 192
Addr_Rhead_length = 0
Addr_Din_base = 448
Addr_Din_length = 111
Send_number = 1
...
************************
************************
Addr_Dout_base = 0x9000
Addr_Dout_end = 0x9000
Addr_Rhead_base = 0x8300
Addr_Rhead_end = 0x8300
Addr_Din_base = 0x8380
Addr_Din_end = 0x845e
```

**这段尾注怎么读（我核对过程序，结论可用）**：

- 原语对象里的 `Addr_*_base` 存的是**相对 Mem2 基址 0x8000 的字节偏移**（[../primitive/](../primitive/) 里 `Prim_09_Router` 用 `Addr_Dout_base + 0x8000`，以及 [code_generator/primitive_json.py:442-444](code_generator/primitive_json.py#L442-L444)）。所以尾注里的 `0x9000` = FPGA 输出口，`0x8300` = R_lab 区，`0x8380` = R_IO 区起点。
- 但上面那半段 key=value 里的数字**单位不统一**，别一律乘 4：
  - `Addr_Dout_base` 打印的是**字地址**（`Addr_Dout_base >> 2`）：1024 ↔ 0x9000−0x8000=0x1000 ✓
  - `Addr_Rhead_base` 也是字地址：192 ↔ 0x300 ✓
  - `Addr_Din_base` / `Addr_Din_length` 打印的是**半字（2 字节）单位**（`>> 1`）：448 ↔ 0x380 ✓，111 ↔ Δ0xDE=222 ✓

  （以上三条关系都是从实测数值反推的，与 `Prim_09_Router.__str__` 里的移位写法吻合。真要按寄存器语义用这些数时，去 `primitive/Prim_09_Router.py` 核一遍。）

**42 个文件的分布（实测）**：core (0,0) 有 14 个（`0_Soma2_0x6`、`1_Router_0x9`、`1_Soma1_0x6`、`1_Soma2_0x6`、`2_Axon_0x81`、`2_Soma1_0x5`、…、`6_Axon_0x41`、`6_Soma1_0x5`），其余 9 个 core 各 3～4 个。**这正好印证了 P1 里那份"5 个计算 phase 各用什么原语"的速查表**：conv1 是 `0x81`，conv2/fc1/fc2/fc3 都是 `0x41`，配对的 soma 都是 `0x05`。

### 4.2 `{tb}_description.txt`

位置在硬件目录下，但**由 Python 的 `chip.print_case_spec` 写出**（[behavior_simulator/chip.py:105-155](behavior_simulator/chip.py#L105-L155)），part 1 是概览，`****** separator ******` 之后 part 2 是各 core 各 phase 各原语的参数（**内容与 4.1 的 42 个 `_input/*.txt` 完全重复**，实测两边的"原语参数"条目数都是 42）。

概览部分长这样（原样摘录）：

```
LeNet_002测试用例说明:

chip (0, 0)执行1个step, 3个phase group

phase group 0 执行1个core,执行2个静态原语phase,执行0个即时原语phase,每个phase执行的时钟数为200000个clock
phase group 1 执行1个core,执行7个静态原语phase,执行0个即时原语phase,每个phase执行的时钟数为200000个clock

```

**这张概览表是"检查你的 codegen 有没有把模型切成合理的形状"最省事的入口**：core 数、phase 数、每 phase 的 clock 数一眼可见，不用去翻 JSON。

### 4.3 `output/output_{group}@{phase}.txt`——格式已完全解出

文件由 [functions/output_file_gen.py:11-41](functions/output_file_gen.py#L11-L41) 生成（**这是权威**），格式是：

```
第 1 行：本组 core 数（8 位十六进制，每行都是 8 位十六进制 + 换行）
之后，对组内每个 core（排序：先按 y，再按 x —— 两次 stable sort 的结果）：
    1 行：本 phase 该 core 有输出的内存块数 M
      M == 0 → 这个 core 就这一行，结束
      M >  0 → 每个块 3 部分：起始地址、长度、长度个 32 位数据字
```

**同一 phase 内的多个块按起始地址升序排列**（实测 10 个文件全部满足）。

我用一个脚本按这条规则解析了硬件侧全部 7 个文件，**每个文件都恰好被消费完、剩余 token = 0**：

| 文件 | core 数 | 各核的块（start, length） |
|---|---|---|
| `output_0@1` | 1 | `(0x8400, 3072)` |
| `output_0@2` | 1 | 无块（M=0） → 整个文件就 2 行 |
| `output_1@1` | 1 | `(0x8400, 3072)` |
| `output_1@2` | 1 | `(0x0000, 224)`, `(0x8380, 224)` |
| `output_1@3` | 1 | `(0x0100, 576)`, `(0x0410, 1536)` |
| `output_2@1` | 8 | 第 0 核 `(0x8400, 3072)`，其余 7 核 M=0 |
| `output_2@2` | 8 | 8 核各 `(0x0000, 4)`, `(0x8380, 4)` |

行数也能对上：`output_2@2` = 1 + 8×(1 + 2×2 + 4×2) = **105 行**（实测 1050 字节）；`output_0@1` = 1+1+2+3072 = **3076 行**（30760 字节）。Python 侧的**单核**文件与它同格式，只是**没有第 1 行的 core 数**（实测 `output_((0,0),(0,0))@2.txt` 以 `00000002` 开头，而对应合并文件 `output_1@2.txt` 以 `00000001` 开头）。

**LeNet_002 的 phase ↔ 文件名对照表**（由 `_input/` 的文件名 + `output/` 里的地址双双反推，两者完全自洽）：

| `output_{1}@` / `_input/` 的 phase | 该 phase 在干什么 | 观察到的输出区间 |
|---|---|---|
| `@1` / phase 0 | 追加在开头的 p06(soma2) | `0x8400` 起 3072 字 = **整个 R_IO 区（0x8400–0x8FFF）的快照**；core(0,0)/(1,0)/(0,1) 有，其余 7 核 M=0 |
| `@2` / phase 1 | 数据收发 | `0x0000`×224 + `0x8380`×224（G1 的接收缓冲 + 图像区） |
| `@3` / phase 2 | conv1 + maxpool1 | `0x0100`×576（pool1 输出）+ `0x0410`×1536（卷积暂存） |
| `@4` / phase 3 | conv2 + maxpool2 | `0x0410`×640 + `0x0690`×100 |
| `@5` / phase 4 | fc1 | `0x0100`×128 + `0x0400`×32 |
| `@6` / phase 5 | fc2 | `0x0100`×96 + `0x0180`×24 |
| `@7` / phase 6 | fc3 | `0x0400`×32 + `0x0800`×4 |

每个计算 phase 都是"两块"：**axon 写回的 V 区 + soma1(pX5) 的输出区**，顺序由地址决定。地址与 P1 那份速查表 B 对得上（`0x0100` pool 输出区、`0x0400` FC1 输出区、`0x0180` FC2 输出区、`0x0690` pool2 输出区）。

> **一处对 P1 速查表 B 的细化**：`0x0800`（P1 里标的"最终结果"）在 `output_1@7.txt` 里只有 **4 个字**；而 `batch_test_lenet.py` 真正读的 10 个分类分数，是 `output_1@7.txt` 的 **`0x0400` 那一段的前 10 个字**（它的 `parse_output` 取 `lines[4:14]`，我逐行核对过：`fffd8028, ffffcc19, ffff72b4, 0000555d, ffff7535, 00017949, fffe1855, 00003ba1, fffc3afd, fffdc578`，正好 10 个，即 axon 的 V 区、`Cut` 之前的 logit，softmax 用不到统一缩放所以不影响结果）。

### 4.4 `cmp_out/`——真正被对拍的文件

命名规则在 [util/name_generator.py:20-31](util/name_generator.py#L20-L31)：

```
cmp_out_{chip_x}_{chip_y}_{phase_group}_{core_x}_{core_y}@{step}_{phase}.txt
例：cmp_out_0_0_1_0_0@0_1.txt  = 芯片(0,0)、group 1、core(0,0)、step 0、phase 1
```

内容 = 单核的 phase 输出，**但去掉了第 1 行的"块数 M"**（[behavior_simulator/chip.py:210-213](behavior_simulator/chip.py#L210-L213)，写的是 `out_list[1:]`），也就是每个块只剩 `起始地址 / 长度 / 数据`。实测 `cmp_out_0_0_1_0_0@0_2.txt` 开头是 `00000100` / `00000240`，即 `(0x0100, 0x240=576)`——正是上表 conv1 的 pool 输出区间 ✓。

> ⚠️ **`cmp_out` 的 phase 从 0 起，`output/` 的 phase 从 1 起**，两者差 1。同一份内容：`cmp_out_...@0_1.txt`（phase=1）对应 `output_1@2.txt`。**这是这套输出里最容易读错的编号。**

数量对比（LeNet_002，实测）：Python 侧 `cmp_out/` 25 个文件，硬件侧 21 个 + `phase_cnt.txt`。**两边共有的 21 个文件逐字节完全一致**（`cmp -s` 全通过）——这说明这份参考输出是"跑通"的状态，可以放心当基准。Python 侧多出 4 个（`cmp_out_0_0_1_0_0@0_3..@0_6`），因为硬件侧这次只落盘到 G1 的 phase 3（见 5.2）。

### 4.5 `cmp_out/phase_cnt.txt`

```
chip (0,0), group :   0, step :   0, phase :   0, finish clock : 1544
chip (0,0), group :   1, step :   0, phase :   0, finish clock : 1544
chip (0,0), group :   2, step :   0, phase :   0, finish clock : 1544
chip (0,0), group :   2, step :   0, phase :   1, finish clock : 1565
chip (0,0), group :   0, step :   0, phase :   1, finish clock : 1775
chip (0,0), group :   1, step :   0, phase :   1, finish clock : 1896
chip (0,0), group :   1, step :   0, phase :   2, finish clock : 11940
```

- 每行 = 一个 (group, step, phase) 的**结束时钟**（单位 clock，不是秒）。phase 从 0 起，与 `cmp_out` 一致。
- 实测这 7 行与硬件侧那 7 个 `(group, phase)` 组合**一一对应**（`output/`、`output_dbg/`、`Rcmd/`、`cRcmd/` 也都是这 7 个组合）。所以它其实是"硬件仿真到底跑了哪些 phase"的清单。
- 看趋势：数据收发 phase（group 0/1/2 的 phase 0）都停在 1544；G1 的 conv1（phase 2）跳到 11940——**这个数就是"一个 phase 要等多少 clock"的实感来源**，配 `clock_in_phase=20_0000`（每 phase 200000 clock）的余量很足。
- 配套的还有 `check_time_out()`（[functions/output_file_gen.py:44-56](functions/output_file_gen.py#L44-L56)）：它会在 `cmp_out/` 里找 `timeout-` 开头的文件并打印超时的 (chip, group, step, phase)。**如果硬件仿真超时，第一个提示在这里。**

### 4.6 `Rcmd/Rcmd_{group}@{phase}_{chip}.txt` 与 `cRcmd/cRcmd_...`

- 硬件仿真期间往芯片发的**读命令流**（把 core 内存读回来看结果）。
- `c` 前缀版 = **带注释版**（`c` = comment），内容一字不差，只是每行后面追加了注释；两者行数相同（各 3072 行，104 KB / 328 KB）。文件名里的 `_{chip}` 是芯片编号（单芯片恒为 `_0`）。
- 注释长这样：

```
00088420000002ad5000000000007f08  //Read CMD: Core x = 1 y = 0 Mem Start_Addr = 8400 Len = 3071 cnt = 0
```

  → "读芯片上 core(1,0) 的 Mem2，从字节地址 0x8400（= R_IO 区）读 3071 个字"。**这正是 4.3 里 `(0x8400, 3072)` 那个块**——两条证据互相印证，也说明这套输出是自洽的。
- 什么时候看它：当你想确认"硬件读回来的到底是不是我以为的那块内存"，或者某个 `cmp_out` 文件对不上时，用它反查硬件读的地址区间。

### 4.7 `hwinit.txt` / `chwinit.txt`

- 芯片**初始化命令流**（把所有寄存器和内存初值写进去）。`c` 前缀版带注释。
- 两者行数完全相同（369824 行），文件大小 3.7 MB / 19.6 MB——**大小差 = 注释**。
- 文件头 4 行（`hwinit.txt` 里没有注释，`chwinit.txt` 里能看见字段名）：

```
00000000   //FileInfo: Filesize
00000101   //Version
00000000   //Time
000186a0   //Simulation Clocks     ← 0x186a0 = 100000 = map_config['sim_clock'] ✓
```

  再接 8 行 `Chip Enable`、若干 `Comments`。**`0x186a0` 与 `sim_clock = 10_0000` 相等，这是你验证"我的 sim_clock 有没有正确传到硬件"的最快检查点。**
- `init_data` 里的权重/激活初值也在这里面——**文件巨大就是因为整个 Mem0/Mem1 的初值都在这**（LeNet 的 fc1 权重就有 12800 字）。

### 4.8 `hwconfig_0_0.txt` / `chwconfig_0_0.txt` / `hwcfg_ck_0_0.txt` / `chwcfg_ck_0_0.txt`

四个文件是"写配置"和"回读配置" × "无注释/带注释" 的组合：

| 文件 | 方向 | 注释里的样子 |
|---|---|---|
| `hwconfig_0_0.txt` / `chwconfig_0_0.txt` | **写**（主机 → 芯片） | `//Write CMD: Chip Registor Start_Addr = 010 Len = 11 cnt = 0` |
| `hwcfg_ck_0_0.txt` / `chwcfg_ck_0_0.txt` | **回读**（芯片 → 主机，`ck` = check） | `//Read CMD: Chip Registor Start_Addr = 010 Len = 11 cnt = 0` |

- 文件名里的 `0_0` 是**芯片坐标**。
- 注释里的 `Start_Addr = 010` 是**十六进制**的寄存器起始地址（`010`→0x10），`Len` 是长度，`cnt` 是批次计数。
- 对应关系：`hwconfig` 行数 369164、`hwcfg_ck` 行数 369154，几乎一样——说明"写什么就回读什么"，这本身就是一种自检。
- **实用技巧**：`hwcfg_ck_ck` 是"硬件实际生效的配置"的完整记录，和 4.1 的 `_input/*.txt`（Python 期望的配置）对比，就能定位"我配的参数和硬件收到的参数不一致"这类问题。仓库里的 [mapping_utils/extractregister.py](mapping_utils/extractregister.py) 就是干这个的：它把 `chwcfg_ck_0_0.txt` 按 core 拆成 `RDcoreMem{core_id}.txt`，或者只抽取地址以 `9` 开头的行（Mem3/FPGA 口）。注意它是**带硬编码 case 名的示例脚本**（`case_name = 'ST_041'`），要用得先改。

### 4.9 `output_dbg/output_dbg_{g}@{p}.txt`——**未能完全解出，先别依赖**

- 相对 `output/` 它**没有第 1 行的 core 数**，直接进数据。
- 但行数差**不一致**：`output_dbg_0@1` 比 `output_0@1` 少 3 行，`output_dbg_2@1` 少 3 行、`output_dbg_1@3` 少 5 行。**用"去掉 N 行头"的假设解释不了。**
- 结论：**它大概是硬件侧的另一种落盘视图（`output_dbg_2@1` 里 8 个核的块似乎仍带各自的小头），但编码我没有确认。要用它的内容之前先自己核对一遍。** 调试优先用 `output/`。

## 第 5 步：拿这些文件做调试（三条回路）

### 5.1 回路一：核对"我的 codegen 配了什么"

`_input/{phase}_{PrimName}_{PIChex}.txt` ↔ `prims.py` 的调用参数。**codegen 生成的每个原语，参数都应该能在这 42 个文件里找到对应的一行。** 这是把 `onnx2prim` 的输出和手写映射对齐时最直接的证据链。

### 5.2 回路二：核对"地址用得对不对"

`output/output_*.txt` 的块地址 ↔ 你规划的地址表。比如上表 `@3` 落在 `(0x0100, 576)` 和 `(0x0410, 1536)`，就应该和你为 conv1 分配的 pool 输出区、卷积暂存区完全一致。`Rcmd/` 又独立地记录了同一批地址（`Mem Start_Addr = 8400 Len = 3071`），两条证据互相印证。

### 5.3 回路三：核对"两边结果一致吗"

`run_test()` 最后做的就是这件事：

```python
for file_name in os.listdir(Path.simulation_cmp_out_dir(tb)):   # 遍历 Python 侧
    parts = file_name.replace('.txt','').split('@')
    if len(name_prefix) >= 6 and len(suffix) >= 2:
        file_group = int(name_prefix[3])       # ← see below
        file_phase = int(suffix[-1])
        if file_group not in test_groups or file_phase not in test_phases:
            continue
    result = self.compare_cmp_out_dir_result_for_one_file(...) and result
```

**关于 `test_group_phase=[(0,1)]` 的实际效果**（实测，不是推断）：

- 它被拆成 `test_groups = {g for g,p in ...} = {0}`、`test_phases = {p ...} = {1}`。
- 而文件名拆出来的 `name_prefix` 是 `['cmp','out',chip_x,chip_y,group,core_x,core_y]`，**`name_prefix[3]` 是 `chip_y` 而不是 `group`（group 在 `[4]`）**。所以真正生效的条件是"`chip_y == 0` 且 `phase == 1`"。
- 在 LeNet 这种单芯片（`chip_y` 恒为 0）配置下，它等价于"**比较所有 group 的 phase 1**"。实测选中 10 个文件：`cmp_out_0_0_0_1_0@0_1`、`cmp_out_0_0_1_0_0@0_1`、`cmp_out_0_0_2_{0..7}_1@0_1`；LeNet_002 的这 10 个文件两边都存在且一致，所以 `assert` 通过。
- ⚠️ **这是一处 off-by-one**（group 应该取 `[4]`）。它在单芯片、`chip_y==0` 的用例里"碰巧"给出一个更宽松、也更有用的过滤（数据收发 phase 各核都对一遍）。**你以后写自己的对拍脚本时，别照抄这一行。**
- 另外注意：`test_group_phase` 只影响 `cmp_out` 的比对；`output/` 那两套文件**永远不参与**。

**`assert tester.run_test()` 到底保证了什么**：

| 平台 | `run_test()` 返回 | 含义 |
|---|---|---|
| Windows | `compare_cmp_out_dir_result()` 的与结果 | 真跑了 exe，并且两边 `cmp_out` 全部一致 |
| 非 Windows | 恒 `True` | **只跑了 Python 侧**；不保证硬件一致，只保证 Python 侧没崩 |

所以我 1.2 那个最小驱动在语义上≈"非 Windows 的 run_test"，**适合迭代 codegen，不能当成验收**。

### 5.4 顺便回答一个常见疑问：为什么参考输出里硬件侧只到 conv1？

实测 `simulator/Out_files/LeNet_002/` 里，`output/`、`output_dbg/`、`Rcmd/`、`cRcmd/` 都只有 **7 个 `(group, phase)`** 组合，`phase_cnt.txt` 也只有 7 行，最深到 G1 的 phase 3（conv1）；而 Python 侧一直算到 `output_1@7`（fc3）、`cmp_out_...@0_6`。原因我没有确认（可能是那次 exe 运行未跑完，或 exe 只对部分 phase 落盘）。**要紧的是：两边共有的 21 个 `cmp_out` 文件全部一致，所以这份参考输出仍然可用。**
